# 购卡订单顾客信息与未使用退卡保护

2026-10-28，D:\RPB。已提交、推送并生产部署，功能版本 `b3542f051d8279c4671710a40d47116ba25f5a73`。发布验证见 `docs/development/CARD_PURCHASE_CUSTOMER_REFUND_PRODUCTION_RELEASE_20261028.md`。

## 变更

- 员工购卡订单显示真实顾客姓名及电话；只有一个时显示现有值，资料不可用时明确提示，不显示截断 UUID。
- 服务端员工订单查询先沿用原门店订单权限，再经共享 CustomerDirectoryQuery 批量读取本租户、本页涉及的有效顾客。客户资料职责仍在 customer 模块，不逐订单发起顾客查询。
- 服务端批量计算 `refundable`，页面对不可退订单显示禁用的“不可退卡”；资格未返回时也默认禁用，不打开退款表单。未使用订单仍要求退款凭证、原因及确认。
- 已有退款服务原本就在卡行锁下拒绝有任何核销记录的卡，本次保留该校验。核销一次后即禁止退款，之后冲正也不会恢复资格。日额度未用过期不是实际使用，不改变原退款政策。

## 排查与审查

根因：CardPurchasePanel 截取 customerId 前八位；原 Purchase 只有 ID。另一个界面缺口是已使用卡仍显示可点击的退卡按钮，实际退款服务会拒绝。

API：员工 GET purchases 增加可空姓名、电话及布尔退款资格，订单扁平字段、分页及权限不变；顾客端和收款/退款命令 DTO 不变，不返回邮箱或认证资料。合同见 `docs/api/2026-10-25-catalog-cards-contract.md`。无迁移、无新增权限、无租户/门店范围调整。预约、排队、Walk-in、就座和清洁无业务变更。

代码审查：订单授权先于顾客查询；顾客 SQL 同时限定 tenant、请求 ID、active、deleted_at；退款资格 SQL 限定 tenant/store/订单，最终写入仍依赖原事务锁和使用记录校验。前端不自行计算已用次数，不以恢复后的余额判断“从未使用”。
