# 钱包两端 UI 与流程重组

目标：员工快速发起收款/充值，顾客快速出码/扫码；首页、操作页、账单列表和原单详情各有单一职责。参考支付宝的快捷入口和 Alipay+ 的确认/结果/详情层级，继续显示 RPB 统一门店品牌、经营主体与 SGD 金额。

## 页面与模块

- 员工：首页（操作入口）→ 扫码/选客收款 → 金额 → 独立原单详情；充值 → 独立充值确认页。账单列表分消费/充值，提供状态筛选与分页，只列概要及详情链接。经理设置、对账、退款及异常处理从“更多”进入，不放在收银首页。
- 顾客：首页（余额和快捷入口）→ 付款码 / 扫商户码；账单列表 → 原单详情 → 查看拟扣与补付 → 本人确认 → 原单结果。流水单独一页，不在首页展开历史账单。
- 两端使用独立路由与模块组件；页面返回、刷新及深链接可恢复原单。员工选客/扫码状态仅在当前门店工作区内存保存，不把付款码放进路由或存储。切换门店清空选客和码。
- 保留 `/wallet/{storeId}#bill=...`、`#receipt=...` 的老链接，登录后转到新详情页；不同门店扫码正确转向目标门店，过期/无权限/无记录清晰显示。

## 不变规则

原子扫码建单、幂等、60 秒付款码、本人确认、余额不足只扣可用余额、剩余应付、三渠道线下核实、归档顾客限制及商业门禁保持。禁止自动扫码扣款、在线支付按钮或复制租户/顾客资料。单店到期仍能查看原账单、流水并按原规则善后。保留所有无关改动，本轮只完成本地实现验收，不自动提交部署。

## 查询契约增量

员工 `GET /bills`、`GET /topups` 可选 `offset=0,status=all`；每页 100，status 只允许 all/pending/completed/closed。默认请求兼容。新增员工 `GET /topups/{id}` 与顾客 `GET /bills?offset=0&status=all`，只读原有 DTO，服务端按租户、当前门店、本人顾客过滤；到期查询保留，非法分页/状态 400。本地白名单仅增加上述两条 GET，仍经过原身份检查，不新增写权限或数据库迁移。

## 验证清单

- PostgreSQL：本人/他人、其他租户/门店，已付/未付/取消、零钱包分录的账单、分页与非法参数、到期可读。
- 前端：入口不渲染完整账单、列表不渲染资金表单；原子建单仅一个请求；旧 hash、跨店扫码、切店清理和响应丢失重试；支付确认显示扣款及补差；隐藏无权限操作。
- 构建及相关后端回归；本地原生数据库运行验证，浏览器检查桌面和手机尺寸、中英文、空/加载/错误/过期状态；不操作生产业务数据。

设计参考：https://cschannel.alipay.com/mobile/helpDetail.htm?help_id=201602030903 及 https://docs.alipayplus.com/alipayplus/alipayplus/uxg_mpp/mpp_overview 。

## UI / 代码 / 查询复核

- UI：操作、列表、原单结果分离；加载、空、错误、到期及无权限分支保留。余额变化导致的旧预览立即清除，要求重新核对；已知失败与网络响应丢失分开处理，后者保留幂等重试。
- 查询：租户/门店/顾客过滤在服务及仓储执行；新增输入为有限状态枚举及有界分页，SQL值参数化。复用现有门店时间和账户时间索引，无表、索引、权限或迁移变动。
- API：原有默认列表兼容；只新增历史查询和充值详情GET。白名单仅增加这两个GET匹配，仍由原员工/顾客身份与商业门禁检查；写接口、扫码校验/建单/绑定事务和资金记账保持。
- 复核结论：本轮自审无未解决的P0/P1。真实手机摄像头、文件图片选择和微信内置浏览器权限本轮未重复实机验收；扫码解析组件沿用既有实现，当前覆盖可见二维码本地解码、页面码值识别及服务端校验。
