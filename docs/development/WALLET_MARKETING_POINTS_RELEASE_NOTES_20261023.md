# Release Notes

## Version / Date

2026-10-23，D:\RPB 钱包营销与手动积分开发版。保留原工作区改动；本轮不提交、不推送、不部署。验证结果与运行范围见同目录 WALLET_MARKETING_POINTS_ACCEPTANCE_20261023.md。

## New

- 钱包营销独立模块：基础档、活动草稿/修订/发布/停用/归档、起止时间与优先级。默认活动草稿为充100送10、充300送50、充500送80、充1000送200，商户可修改；每次申请只选择一档，不支持叠加、数量或客户端指定赠送。
- 顾客单档选择、直接确认充值、付款声明、取消与历史。商户核实实际本金收款后才增加本金及赠送；声明付款不会入账。无活动时基础档1:1，员工仍可登记普通自定义金额充值。
- 手动积分独立账本：加分、扣分、兑换内容记录、管理员全额冲正与顾客明细。不抵现金，不参与钱包账单，不含商城配送。

## Changed

- 充值、顾客确认支付、商户扫码支付共用资金批次分摊；账户、消费单、流水与报表拆分本金和赠送。
- FIFO依入账次序使用批次；批次冻结充值时的比例及扣款规则，支持按比例或先本金后赠送。后续配置变更不改原单。
- 原消费退款恢复原批次和原分项；混合支付退款预览与提交使用相同原渠道比例分摊。活动充值第一版只允许退出该批剩余权益：冻结剩余本金和赠送，实际退本金，完成时撤销剩余赠送；取消则释放冻结。仅剩赠送时走无现金的独立赠送退出。
- 资金操作加入组件版本头，退款创建需预览账户版本。旧页面须刷新后才能确认入账、扣款、退款或撤赠，避免旧单余额模型误解释赠送。

## Fixed

- 现金充值仍可留空纸质收据，由现有内部引用保持幂等；不会把赠送算作外部实收。
- 幂等结果兼容旧JSON全本金默认值；派生展示字段为只读，支持完整回放。
- 营销仓储通过方法访问Spring代理目标，限流保留独立事务；积分开关查询保持真正只读。

## Migration

新增 V059–V062，仅在指针PostgreSQL的新建隔离schema执行验证。

- V059：本金/赠送分量、充值批次、流水分摊、退款冻结、赠送退出及延迟完整性约束；旧余额与冻结全部按历史本金池迁移，不伪造旧充值批次。旧未使用消费报价失效，要求重新核对。
- V060：营销配置、活动修订、档位、报价、顾客申请来源/声明/快照与限流。
- V061：独立积分计划、账户、追加流水、兑换、幂等、审计及钱包到积分的绑定；保护已有积分顾客身份。
- V062：既有租户管理员/门店经理获得新模块权限，不自动给普通员工或平台账号授权，不新增产品线订阅。

## Permission

新增 wallet.marketing.view/manage 与 wallet.points.view/grant/adjust/redeem/reverse；继续使用钱包App Gate、经营主体共享计划、租户及门店访问范围。营销配置涉及同一计划所有关联门店，修改人须有相应门店管理权限。积分只读选客及上下文可独立使用points.view，不能借此读取资金账户。冲正同时要求管理员角色和reverse权限，并校验原记录门店权限；到期或停用后仍允许有权限的原单善后。

## Risk

- 后续发布须前后端同批升级，并先备份数据库；活动草稿不自动发布，自助充值与手动积分默认关闭。
- 多门店同主体共用计划与活动；赠送不是实收本金、现金或可直接提现额度。
- 本地验收使用测试会话、测试顾客与模拟线下实收；二维码图片识别不等同于手机摄像头实测。不接短信或在线支付。
- 共用顾客生命周期现在同时保护积分记录；预订、排队、叫号、清台的业务流程没有改动。

## Rollback Notes

产生本金/赠送或积分分录后，不能简单降级至旧版钱包jar，也不能删表/改余额抵消流水。紧急止损优先关闭活动、自助申请及积分新写，保留查询、已收款原单确认和退款/冲正善后。程序回退需使用支持相同组件账务模型的兼容构建；必须恢复发布前快照时，须先完整核对切换后的实收、退款、赠送及积分流水，单独制定数据恢复方案。


## 追加优化：PayNow 与顾客直接确认

营销充值显示计划允许的现金、PayNow、信用卡；PayNow 未完成本门店收款配置时保留选项、禁用并明确提示，配置完成后可选。商户在钱包设置维护原有共用 PayNow 资料；不自动替商户启用原本关闭的渠道。

顾客选择一档和付款方式后直接“确认充值”，报价在后台校验，不再展示独立报价按钮。网络不确定重试复用有效报价及幂等键；过期、配置变化及旧门店响应不会绕过服务端校验。待核实单展示本金 PayNow 收款码，赠送金额不计入银行收款。

本次追加无迁移、无权限新增、无新端点；列表 channels 语义改为计划允许的渠道，能否付款继续由 context.paynowConfigured 与服务端共同控制。旧前端已有 PayNow 禁用判断。回退此追加优化须使用同一组件账务模型的兼容版本，不能回退至旧单余额模型。本轮仍未提交、推送或部署。
