## 问题与证据

20000000原演示门店新增排班提示“必填项、日期范围（最多31天）和规则”。只读生产核查显示：员工1002当前状态active且enabled，但leave_date为2026-09-20；所排营业日期2026-10-30已超过离职日。早班11:00–23:00正常，未创建该日排班。

根因：保存已按入离职和门店任职日期检查，但员工选项只按active/enabled和未结束门店关系查询。表单会让不可排班员工被选中，所有400又共用31天提示。没有修改该员工档案、日期、状态或线上排班，不通过清除离职日期绕过业务校验。

## 模块与接口契约

- SchedulingRepository负责候选查询：员工雇佣区间、门店任职区间与查询日期范围必须有共同交集。入职日与离职日包含当日；门店ended_on延续原有排除结束日规则。SQL同时限定tenant_id、store_id及关联员工，不增加逐员工查询。
- ScheduleService保留权限、规划锁、员工锁、版本检查、幂等及重叠规则；正常保存仍在锁内核验资格。无门店任职记录的未知／外店员工先返回任职不匹配，避免通过细分错误探测其雇佣状态。符合资格的正常写入不增加额外查询，仅失败路径补查门店归属。
- ScheduleEditor沿用GET /api/v1/stores/{storeId}/workforce/schedule?from=日期&to=日期，以单个营业日期获取候选；切换日期刷新，旧请求取消且旧响应不能覆盖新日期结果。加载中或失败时禁止保存，失败可重试并保留班次草稿。
- 初始外部员工编号必须在候选名单内才能预选，不能把外店／伪造ID填入表单。已合法选中过的员工在新日期失效时显示禁用选项与说明，不悄悄换成其他员工。无候选显示明确提示。
- 历史排班items及快照不随候选过滤隐藏或修改；编辑页保留原员工名。原排班取消／删除和未知提交结果的恢复逻辑继续使用原版本、UUID及请求体。
- 双语排班错误在scheduleEligibility.ts集中定义，phaseText复用；不把判断塞入通用API或员工维护模块。

既有GET与PUT路径、DTO及鉴权不变。GET的employees表示请求区间内至少一天具备资格的候选；不是历史items的过滤条件。只有管理员获得候选，员工本人查询仍不返回候选名单。普通列表、批量排班与周复制沿用各自现有职责。

PUT /schedule/{id}的细分业务错误均为400，沿用success=false、code、private/no-store契约：

| 错误码 | 含义 |
| --- | --- |
| WORKFORCE_SCHEDULE_DATE_OUT_OF_RANGE | 不在门店当地今天至未来90天 |
| WORKFORCE_SCHEDULE_BEFORE_HIRE | 营业日期早于入职日 |
| WORKFORCE_SCHEDULE_EMPLOYEE_LEFT | 营业日期晚于离职日 |
| WORKFORCE_SCHEDULE_EMPLOYEE_INACTIVE | 停用或不在职 |
| WORKFORCE_SCHEDULE_STORE_ASSIGNMENT | 该日无本门店任职，或未知／不属于本店的员工 |
| WORKFORCE_SCHEDULE_SHIFT_DISABLED | 班次停用 |

请求格式等其他400继续保留WORKFORCE_INVALID；401/403、409冲突及历史快照规则不变。营业日期仍决定跨日班次归属，不按实际开始或结束自然日重新分类。
