## 1. 目标与确认范围

建设独立共享产品目录，以及接入钱包的免费集次卡、付费次数卡和周期卡。产品目录供不同业务模块调用，业务流水分别保存。

### 1.1 已确认需求

| 编号 | 需求 |
|---|---|
| R01 | 产品单独一个模块，有分类，支持中英文录入、价格、含税/未含税、上下架。 |
| R02 | 产品目录供卡业务、未来寄存酒、积分商城、自助购物共享，不重复建立产品资料。 |
| R03 | 免费卡支持签到或消费集次，累计 N 次赠送一次服务、指定消费权益或赠品。 |
| R04 | 付费卡购买后获得指定商品或服务的使用次数，如 200 元购买 30 次。 |
| R05 | 支持周期有效、每日使用次数，以及总次数与每日限额组合。 |
| R06 | 每日额度当日有效，过期不候，不累计、不顺延、不补发。 |
| R07 | 支持商户扫描顾客码，以及商户出码、顾客扫描确认的增扣流程。 |
| R08 | 模块化设计，资金、积分、购卡、集次、奖励、卡核销分开记录。 |

### 1.2 本方案建议默认值

以下为设计建议，不冒充用户已逐项确认的业务规则。进入对应开发任务前应将有实际影响的选择落实到合同或配置。

- 产品为租户共享资料，门店范围、价格与渠道投放单独维护；禁止跨租户共享私有产品。
- 卡首版本店使用；需要跨店时，明确限定同经营主体、适用门店及统一权益时区。
- 卡内次数为正整数；寄存量、重量等可分数量由未来对应业务定义，不复用卡次数精度。
- 卡不可转赠、转售或提现；不默认支持自动续费或循环扣款。
- 免费卡由商户核实后集次，不在首版自动根据钱包付款增加次数。
- 集满生成独立奖励权益，顾客可以以后兑换；是否循环及奖励有效期在发卡规则中明确。
- 产品中英文至少填写一种，另一种允许后补；缺失时回退已有语言。
- 共用钱包入口和商业授权，卡功能有独立权限及开关；产品目录是共享基础模块，不自动授权其他产品线。

### 1.3 本期与后续边界

本期包含：产品分类与资料、基础税价、门店范围及渠道投放基础、集次卡、奖励、购卡、次数/周期权益、双向扫码、冲正、独立流水及查询。

未来寄存酒、积分商城、自助购物本次只约定集成边界，不实现这些业务的订单、寄存操作、履约或完整页面。库存、复杂促销、多规格组合、批次成本、自动支付网关另行规划。首版提供一个默认可引用的产品项目，未来可扩展 SKU，不预先实现完整 SKU 系统。

## 3. 架构方案与职责

采用现有 Java 21 / Spring Boot / PostgreSQL / Flyway / Vue 3 / TypeScript 单体架构，以业务模块隔离，不新增微服务或独立 Maven 工程。

比较过两种路线：全部塞入 wallet 子模块，接入较短但会把共享产品和卡规则绑定钱包；独立 catalog/cards 并由钱包适配，接口成本略高但支持后续产品线共享。本方案采用后者。

```text
共享基础：customer / customerauth / tenant / store / auth / appgate
                         |
                      catalog
              产品、分类、税价、门店与渠道
                 ↑       ↑       ↑       ↑
               cards   寄存酒   积分商城  自助购物
                 ↑      后续     后续     后续
               wallet
          入口、身份码适配、支付适配、记录展示
```

| 模块 | 拥有 | 不拥有 |
|---|---|---|
| catalog | 产品、分类、翻译、单位、基础价格、税务配置、上下架、可用范围 | 卡次数、积分价格、顾客寄存量、订单、库存余额 |
| cards/stamp | 集次规则、进度、轮次、达标发奖 | 钱包资金、顾客身份主资料 |
| cards/purchase | 卡方案报价、购卡订单、收款关联、发卡与退款编排 | 直接写钱包资金表 |
| cards/entitlement | 持卡、奖励权益、总次数、有效期、周期额度 | 产品主资料、现金收款 |
| cards/redemption | 核销意图、授权、确认、撤销/冲正 | 另一套独立次数余额 |
| cards/history | 卡业务流水查询及统计 | 修改业务账本 |
| wallet/integration | 钱包与卡的应用接口适配 | 卡规则和产品资料 |

依赖规则：catalog 不依赖 cards/wallet；cards 通过 catalog 应用接口读取产品，通过自身支付端口请求收款；wallet 适配端口，不反向调用卡核销造成循环依赖。Controller 不访问 Repository，跨模块不直接写表。

## 4. 共享产品目录

### 4.1 产品与分类

- 分类：租户内编号、中英文名称、排序、启停；首版单层，避免提前引入多级树。
- 产品：租户内唯一编号、中英文名称/描述、分类、图片引用、实物/服务类型、计量单位、版本、创建/修改信息。
- 资料生命周期：`draft -> active -> inactive -> archived`；下架允许按规则重新上架，归档禁止新增投放。
- 门店适用关系：明确允许使用的门店；共享不代表自动全店可用。
- 业务渠道：卡权益、积分兑换、自助购物等分别投放；产品上架不代表所有渠道自动开放。
- 双语是业务数据，与系统 i18n 文案分开保存；分类也支持双语。查询同时支持两种语言及产品编号。
- 编辑使用版本检查，防止两名管理员静默覆盖。已被引用的产品禁止物理删除。

### 4.2 价格与税价

- 基础价格包含金额、币种、含税/未含税模式、税务类别和版本；税率从明确的有效税务配置解析，不硬编码。
- 明确区分应税、零税率、免税/不适用，不用一个 0 表达全部语义。
- 金额使用精确十进制或最小货币单位，禁止浮点金额；首版交易币种沿当前钱包可支持的 SGD，不默认承诺多币种结算。
- 首版支持租户基础价及可选门店覆盖价；缺失覆盖时明确回退基础价，不随机回退其他门店。
- 含税价格：总额保持录入值，税额从总额分解；未含税价格：先计算未税金额，再加税。
- 首版统一按订单行计算，以币种最小单位 HALF_UP 舍入；税额和总额必须守恒。实际开票规则如有不同，应在上线前替换为明确规则版本。
- 报价提供 `netAmount`、`taxAmount`、`grossAmount`、税率、模式、币种及规则版本；服务端计算，不信任前端传入税额。
- 交易保存产品编号、中英文显示资料、单位、数量、价格及税务快照；后续改名、改价或改税不回写历史。
- 卡售价由卡方案定义；兑换积分由商城定义；产品基础价格不能自动转换成次数或积分价格。

### 4.3 下架与历史履约

下架阻止新的销售及新的投放，不自动撤销已售卡、已发奖励和已寄存物品的领取权。历史履约校验使用已发权益快照及明确暂停规则，不能仅要求当前产品仍上架。

紧急停止履约是独立管理动作，需原因、范围、权限和补偿处理；普通下架不能承担此职责。

## 5. 卡方案、权益与周期规则

### 5.1 卡方案类型

| 类型 | 规则 | 示例 |
|---|---|---|
| 集次卡 | 免费领取，合格签到/消费累计，达到目标生成奖励 | 集 10 次送指定服务一次 |
| 次数卡 | 购买后获得总次数，可选有效期和每日上限 | 200 元获得指定产品 30 次 |
| 周期卡 | 有效期内每日固定额度，当日未用作废 | 30 天每天一次 |
| 组合卡 | 总次数、整体有效期和每日上限同时限制 | 总共 30 次，60 天内每天最多两次 |

卡方案保存发布版本；发卡冻结该版本、适用产品、数量规则、门店范围、时区、有效期规则及退款政策。改方案只影响新发卡。

一个权益项目明确引用产品、每次发放数量及单位；首版一个核销行对应一个产品权益，组合套餐后续另行定义。多张同类卡不隐式合并；顾客/商户明确选择本次使用的持卡记录。

### 5.2 集次和奖励

- 分清签到集次与消费集次；每日上限、目标次数、每次增加量、是否循环、进度有效期和奖励有效期均由方案确定。
- 消费集次引用来源交易；同一来源在同一活动内只能入账一次，即使更换幂等 key 也不能重复。
- 首版不启用无法验证来源的自助消费集次；外部小票来源需明确编号和人工核实责任。
- 达标增加进度、完成轮次、发奖励必须同事务；唯一约束保证同一持卡同一轮次只发一次。
- 示例：进度 9，增加 1，生成一份服务奖励；允许循环则转入下一轮。奖励核销与集次记录分开。
- 撤回集次需检查所发奖励；奖励尚未使用时可受控撤销，已使用时禁止简单减进度掩盖履约，进入管理员纠错流程。

### 5.3 每日额度

- 每日额度只在该业务日期有效，未用作废，不累积、不顺延、不补发。
- `dailyLimit`、`usedToday` 与 `remainingTotal` 分开表达；无总次数限制必须明确表示，不使用负数代替无限。
- 业务日期按持卡冻结的 IANA 时区计算，时间戳以 UTC 存储。跨店使用沿用同一权益时区，不能换店重置当日额度。
- 每日区间为本地当天 00:00 至次日 00:00，使用左闭右开区间；整体有效期同样使用 `[startsAt, expiresAt)`。
- 建议购买确认即生效；按自然日有效的 D 天卡，购买当天算第 1 天，到第 D 天后的本地零点结束，购买页明确当天不足整日。首次使用激活作为后续可选规则，不隐式启用。
- 可使用量受当日剩余额度、总次数剩余量和整体有效期共同限制，扣次不得跨过任一上限。
- 日额度通过日期桶及使用记录计算，不依赖午夜任务重置一个共享余额。未用过期量可按规则推导，按日结算时使用唯一日记录，不能伪造成顾客消费流水。
- 核销执行以最终锁等待后的服务端时间判定日期和有效性；跨零点导致报价日期变化时返回过期/报价变化并重新确认，不自动消耗次日额度。
- 冲正恢复原日使用记录；原日已过不能把额度补到今天。总次数可按原单纠错恢复，但已经整体到期的卡不会因此重新可用。

## 6. 购买、收款与退款

购卡状态建议：`pending_payment -> payment_confirmed -> issued`，另有取消、退款处理中、部分退款/已退款状态。必须记录异常待处理状态，不能收到钱却丢失发卡线索。

- 创建购卡订单前服务端生成报价，冻结卡方案版本、顾客、售价、币种、税价快照及有效期。
- 首版沿用人工确认现金/PayNow 等现有渠道的能力，不假设截图上传等于实际收款。
- 经应用端口适配现有收款校验与凭证；新增购卡收款关联，不伪造充值单，也不直接操作钱包 Repository。
- 确认支付后，同一购卡订单只能发卡一次；支付凭证也须有业务防重复约束，不能仅依赖请求 key。
- 本地可原子提交的收款关联和发卡放在同事务；未来外部支付采用持久化支付结果、重试和对账，不跨网络假设数据库原子性。
- 若启用钱包余额购卡，必须独立顾客金额授权，关联原钱包账单和购卡单；财务展示避免同一笔支付重复计算实收。
- 核销一次只记录权益消耗，不再次记录售卡实收。赠送奖励不记作充值余额或收款。
- 退款关联原购卡单和原支付渠道，期间冻结受影响权益并与核销串行化；不能同时退款和继续消费。
- 首版建议仅允许未使用卡全额退款；已使用卡退款不能直接按售价除以总次数擅自折算，需先确定政策。退款失败保留可恢复状态，不删除原记录。

## 7. 双向扫码与授权

### 7.1 商户扫描顾客码

集次：选择活动与数量 → 扫顾客身份码 → 核验来源/当日限制 → 商户确认 → 原子增加进度并按条件发奖。

核销：选择卡及产品、数量 → 建立核销意图 → 顾客逐笔确认，或出示绑定具体核销内容的短期授权码 → 服务端校验 → 扣次 → 双方查看结果。

现有 WI 身份码识别可复用，但本身不授予扣次权限；现有金额限额授权也不能沿用为卡授权。不要求顾客先有储值资金账户才能免费领卡或持有卡权益。

### 7.2 顾客扫描商户码

商户创建一次性集次/核销单 → 出码 → 顾客扫码查看 → 选择持卡并明确确认 → 服务端绑定顾客并执行一次 → 原单展示完成结果。

- 查看/预览不绑定持卡、不增扣；失败不抢占他人权益。
- 未绑定顾客的商户单，确认时原子绑定；两名顾客并发扫描只能一人完成。
- 集次码首版一次性使用，不作为可转发的通用签到海报。
- 新码类型在独立解析器与适配入口注册，不改变现有 money/points 的语义。
- 码仅保存不可逆哈希，建议 120 秒有效，权限、归属、业务门店和内容均需服务端校验；刷新后原码失效。

### 7.3 共同执行约束

- 请求幂等覆盖租户、操作人、操作类型、key，摘要包括门店及实际业务内容；同 key 同内容重放，同 key 不同内容拒绝。
- 业务级去重覆盖原单、消费来源、奖励轮次、支付结果及一次性授权，不因新 key 或另一操作人而绕过。
- 核销单、持卡余额、日期桶、授权消耗、流水、审计及命令结果同事务完成；错误整单回滚。
- 固定锁序：命令锁 → 原核销/购买业务单 → 持卡（按 ID 排序）→ 日期桶 → 授权；所有反向操作遵循同序。支付路径若涉及现有钱包锁，需专项验证，不混用未经证明的锁序。
- 最终阻塞锁之后重新检查时效和日期，不能只在请求入口判断。
- 请求超时保留原编号，先查询结果；404 不代表可安全重新执行。恢复命令与原请求串行化，可关闭尚未执行的请求，阻止晚到请求重复生效。

## 9. API、权限与界面合同

### 9.1 拟定入口

- 目录管理：`/api/v1/tenants/{tenantId}/catalog/...`，明确校验登录租户及管理权限。
- 门店产品查询：`/api/v1/stores/{storeId}/catalog/products`，按实际可用门店与调用渠道过滤。
- 员工卡业务：`/api/v1/stores/{storeId}/wallet/cards/...`。
- 顾客卡业务：`/api/v1/public/stores/{storeId}/wallet/cards/...`，非公开匿名扣次接口，必须顾客会话与归属校验。

命令包括分类/产品编辑、上下架、报价、领卡、购卡确认、集次、奖励发放、核销单创建、授权、确认、取消、冲正、结果查询及恢复。查询接口无业务副作用。DTO 显式定义，不直接暴露数据库实体。

拟定稳定错误语义：资料/报价版本变化、未上架、门店/渠道不适用、权益未生效/到期、总次数不足、当日额度用完、授权过期/已用、重复来源、幂等冲突；分别使用 400/401/403/404/409，响应不泄露其他租户的存在性。

### 9.2 权限与商业门禁

- 目录权限：`catalog.view/manage/publish`；门店价格维护另设可授予权限，不因员工可核销而允许其改价。
- 卡权限：`wallet.cards.view/manage/sell/stamp/redeem/reverse/refund`，区分管理员配置、收银操作、经理冲正退款。
- 目录共享读取由实际调用模块验证其产品线 AppGate 和渠道；不能凭目录可读绕过卡、商城、自助购物的商业授权。
- 钱包及卡开关停用后历史仍可按权限查询；原单退款/冲正采用受控恢复权限，不因关闭新交易而丢失纠错入口。
- 新入口同步审查 Spring Security、CSRF、请求模型版本保护及本地运行 allowlist。不能只添加 Controller 而漏掉安全过滤器覆盖。

### 9.3 页面

- 独立产品管理：分类、双语编辑、价格税务、门店范围、渠道、上下架。
- 钱包顾客端：我的卡包、卡详情、集次进度、可兑换奖励、今日可用量、整体有效期、购卡与扫码确认、独立记录。
- 钱包员工端：卡方案配置、售卡、集次/核销、原单详情、冲正退款、卡统计。
- 所有页面处理加载、空态、失效、权限不足、规则变化、未知结果恢复及门店切换后的旧请求污染。
- 周期卡必须明确展示“当日额度当日有效，未使用不累计”；顾客确认页展示具体产品、数量和扣后余额。

应用接口合同草案（接口及 DTO 随所属任务建立，不使用业务模块 Repository 作为接口）：

```text
ProductCatalogQuery.get(TenantScope, UUID productId, String locale) -> ProductView
ProductCatalogQuery.requireUsable(StoreScope, UUID productId, String channel) -> ProductSnapshot
ProductPricingService.quote(StoreScope, ProductQuoteRequest) -> ProductQuote
StampService.grant(StoreScope, CardActor, StampCommand) -> StampResult
EntitlementQuery.available(StoreScope, UUID customerId, UUID cardId, Instant now) -> Availability

CardCommandQuery.result(StoreScope, CardActor, String operation, String key) -> CommandResult
CardCommandRecovery.reconcile(StoreScope, CardActor, ReconcileCommand) -> CommandResult
```

`CardActor` 为受校验身份上下文，明确员工或顾客及其 ID；不得允许客户端传入 actorId 冒充身份。`ProductSnapshot` 与 `ProductQuote` 包含版本；`Availability` 区分总量、日额度和有效期。核销传入持卡/权益 ID，不能只传产品 ID 猜测扣哪张卡。

## 14. 实施前业务收口与风险

不影响当前文档交付，但对应功能开放前需落实：

1. 产品是否必须中英都填；本方案建议至少一种，另一种回退。
2. 卡生效从购买即刻还是首次使用，按自然日还是完整 24 小时；本方案建议周期卡购买即生效、购买当天计第 1 日并明确提示。
3. 集次何种消费合格、来源范围、是否循环、进度和奖励到期；不能由开发人员凭例子推断。
4. 首版仅线下收款购卡，还是同时支持钱包余额购卡；决定支付适配与回归范围。
5. 已使用卡的退费政策、免费奖励已兑换后的集次纠错方式，以及产品永久停供的替代/退款措施。
6. 是否启用跨店；如启用，需要发行主体、适用门店、统一时区和退款操作门店规则。
7. 实际税务类别、税率来源及适用舍入/凭证要求；本方案定义技术模型，不代替商户确认经营配置。

主要技术风险是：金额与次数授权混用、支付与发卡重复、原单冲正破坏奖励依赖、跨日/跨店超额、下架误伤已售权益、统一报表重复计算实收。各风险均已映射到 T1–T6 的行为测试。
