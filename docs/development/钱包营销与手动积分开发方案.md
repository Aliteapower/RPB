## 1. 已确认范围与设计默认

### 1.1 用户已确认

1. 放在**钱包产品线**，不新增营销产品线、独立登录、顾客档案或软件订阅。
2. 租户商户管理员可设置充值赠送、修改档位、新增档位、停用档位。
3. 初始活动档位：充100送10、充300送50、充500送80、充1000送200；这是种子配置，不是代码中的固定金额。
4. **顾客每笔只能选一档充值**，不能自定义金额、选择多档、填写档位数量或叠加活动。
5. 有活动按活动规则赠送；无活动按1∶1充值。
6. 顾客可自助提交充值，但必须商户确认实际收款，才能入账和消费。
7. 支持两种消费分摊：A 默认按充值活动比例扣本金与赠送金；B 先本金、后赠送金。
8. 积分只做商户手动增加、扣减和兑换记录，**不抵现金、不自动抵钱包账单**；以后可以扩展积分商城，本期无配送。
9. 保持模块化、多租户、共享顾客、发行主体钱包边界和现有扫码流程。

### 1.2 本方案采用的默认规则

下列为使实现可落地而确定的设计默认，不混称为用户逐条确认：

- 顾客无活动时也从基础档位中单选，赠送0；初始基础金额为100、300、500、1000，管理员可改。
- 现有商户手工普通充值在无活动时保留任意合法金额；有生效活动时，新增充值统一要求选一个档位，不提供绕过档位的隐藏赠送入口。
- 同一钱包计划使用同一活动、基础档位和扣款策略；不做同一钱包跨门店使用不同分摊规则。
- 活动可以设时间段及优先级；同一请求只命中一个活动，不叠加。相同优先级的重叠活动禁止发布。
- 订单创建时锁定档位、金额、活动和扣款策略版本；后台后续修改只影响新订单。
- 按充值确认入账顺序使用批次，批次内部执行其冻结的分摊策略。
- 本期赠送金和积分均无自动过期、提现或转赠；不实现自动消费送积分。
- 赠送活动批次的充值退款首版采用“退出该批次当前剩余权益”：退剩余可退本金、撤销对应剩余赠送金；不开放该类批次任意部分本金退款。普通无赠送充值保留既有部分退款；消费退款支持部分退款。

## 2. 当前系统与改造边界

现有 `wallet` 已有主体钱包计划、账户、充值、扫码扣款、顾客扫码账单付款、收款核实、退款、对账、幂等及审计。统一顾客归 `customer`，手机号密码登录归 `customerauth`，现有 `payment` 提供共享收款资料和 PayNow 码能力。

当前 Account 只有总余额与冻结额，Topup 只有实充值金额，消费分录没有本金/赠送拆分。旧退款按统一余额处理。因此新增营销必须同步扩展账务、退款和报表，不能只在充值时把金额相加。

本轮不得改动预约、排队、入座、清洁、支付网关或其他产品的收费逻辑，不复制这些模块。软件订阅费、顾客实收本金、活动赠送和积分四者分别记录。

## 3. 产品与模块设计

### 3.1 对外入口

钱包收银台“更多”增加：充值活动、基础档位与扣款规则、顾客积分、积分记录。顾客钱包增加：充值、充值申请、积分余额与明细。沿用现有充值码、付款码、账单与资金流水入口。

### 3.2 对内职责

## 4. 租户、发行主体及权限

- 顾客档案继续租户级共享；钱包资金和积分权益按**租户+发行经营主体**隔离。
- 当前积分计划与钱包计划一对一绑定；同主体计划门店共享积分账户，不跨租户或发行主体通用。
- 每笔交易记录发生门店，员工必须具有该门店访问权；查询/写入同时验证 tenant、issuer、program、customer。
- 活动、基础档位和扣款规则影响整个计划，管理者必须有配置权限及全部受影响门店的管理范围，单店员工不得改变其他店的共同规则。
- 复用 wallet App Gate，不新建 app_key、不自动授予积分权限，不自动开通 payment 产品。
- 新增权限建议：`wallet.marketing.view/manage`、`wallet.points.view/grant/redeem/adjust/reverse`。分别控制查询、加分、兑换扣分、其他调整扣分及冲正，避免一个按钮赋予全部能力。
- 充值实收确认继续使用 `wallet.collection.confirm`；活动管理员不因此自动拥有确认实收权。
- 产品到期仍可读本人余额、历史、积分，允许既有充值实收核实及原单退款等善后；禁止新活动充值申请、签新码、发积分及兑换。积分原记录纠错仅允许经理专用冲正用例，不伪装为新增赠分。
- 有资金或积分权益的顾客不得直接删除、合并或改归属；扩展既有顾客权益保留检查端口，不把积分检查写进顾客控制器。

## 5. 档位、活动和报价

### 5.1 种子数据

| 初始活动档位 | 实收本金 | 赠送 | 合计可用 |
| --- | ---: | ---: | ---: |
| 充100送10 | 100 | 10 | 110 |
| 充300送50 | 300 | 50 | 350 |
| 充500送80 | 500 | 80 | 580 |
| 充1000送200 | 1000 | 200 | 1200 |

基础充值档位单独保存同组初始本金、赠送0。新功能启用时只初始化可编辑基础档位和**草稿活动模板**，不自动给现有商户发布赠送活动，不自动赠送历史充值。

### 5.2 配置与生命周期

活动包括名称、说明、计划、时区、有效期、优先级、版本和档位列表。列表长度可配置，上限首版50，至少一个有效档位。档位本金>0，赠送>=0，合计不得超钱包金额上限；同一活动不能有两个本金相同但赠送不同的可选档位。

持久状态 `draft/published/disabled/archived`；待开始、进行中、已结束由发布状态和服务器时间推导，不依赖定时任务改状态。有效区间为 `[startAt,endAt)`。门店时区只用于录入和显示，数据库存 UTC instant。发布后版本不可原地修改，修改生成新版本。

同一计划选择最高优先级的已生效活动；无活动使用基础档位。新活动或版本发布后，已创建申请的冻结权益不自动变更；停用阻止新申请，已有待核实订单保留原规则，但仍需按原单核实真实收款。

### 5.3 每笔单档

API 只接受一个 `offerId` 及报价标识，**不接受 offers 数组、quantity、客户端赠送金额**。一笔活动充值的 principal 必须等于选中档位的本金，不能把两档拼成一单。服务端验证选择仍可报价，金额以服务端为准。

选择报价与创建申请是两个步骤：报价有效5分钟；创建时重新验证活动/版本/时间。报价后活动停止、过期或版本变化，返回“活动已变化，请重新选择”；已经成功创建的订单不重新套新活动。幂等重放优先恢复原成功订单，不因为报价过期重复建单。

## 6. 顾客自助充值及商户充值

### 6.1 顾客流程

手机号密码登录 → 查看当前活动及单档列表 → 单选一档 → 查看本金、赠送、可用合计与说明 → 选择当前可用线下收款方式 → 提交充值申请 → 付款/交款 → 等待商户核实 → 入账后可用。

- 本期仍不接短信或线上收单；PayNow 使用当前商户收款资料展示码，现金到店交款，信用卡为商户线下终端，不在顾客网页输入卡号。
- 顾客页的“已付款”只登记声明与时间，不改为 paid、不确认收款，不触发积分或余额写入；截图也不自动入账。
- 顾客身份只取会话，不允许正文传别人的 customerId/accountId。首次申请可在同一事务幂等开通本人零余额账户，不要求员工先开户；顾客必须有已确认共享手机号、有效资料、有效计划和合规来源门店。
- 同一顾客、计划最多存在一个自助待收款申请（pending_collection/verified_pending_credit）。原申请可继续查看或在未核实时取消；不会因双击/刷新出现多笔待单。异常单移入经理善后队列，不永久占用新待单额度；提交限流与待单唯一约束同时实施。
- 不自动过期取消待收款单，避免线下已经转账但原单消失；顾客或员工取消后的迟到实收进入现有异常实收/原渠道退款流程，不能复活原单赠送。

### 6.2 商户流程

扫码充值码或搜索共享顾客 → 有活动时单选档位；无活动时可选基础档或使用现有普通金额入口 → 创建待收款单 → 核实**本金实收金额** → 确认入账。

确认页同时显示“应实收100 / 本金100 / 赠送10 / 合计到账110”，禁止把110误作应收现金。普通现金收据继续选填，PayNow、信用卡、补差及异常收款凭据要求保持原规则。

商户“待核实充值”同时列出顾客申请和员工创建订单，显示来源、顾客、手机号、活动快照、应收本金、提交时间和付款声明。商户可确认或取消，不能暗改已提交档位、渠道、金额及赠送；需变化时取消并重新建单。

### 6.3 事务与状态

保留既有 `pending_collection → credited` 及 cancelled、exception、verified_pending_credit 兼容状态。`customerDeclaredPaidAt` 是独立声明字段，不增加可伪造的资金成功状态。

确认事务须一起完成：幂等锁 → 账户锁 → 充值单锁 → 验证实收与原单 → 收款记录(仅本金) → 资金批次(P/G) → 本金/赠送组件与合计流水 → 余额/版本 → 充值状态 → 审计及幂等响应。任一步失败全部回滚。

取消/确认并发依赖同一充值单锁，只能一个终态成功；成功后重试返回原结果，不重新赠送。未知网络结果通过原请求重试或查原单恢复，不另起新订单。

## 7. 消费、分摊及二维码

总可用=(本金余额-本金冻结)+(赠送余额-赠送冻结)。先按入账顺序选可用批次，再在批次内分摊；历史余额使用100%本金的迁移批次。多批次混用不得拿全账户平均赠送比例重新计算。

| 分摊策略 | 本金100+赠送10，消费55 | 剩余 |
| --- | --- | --- |
| proportional（默认） | 本金50、赠送5 | 本金50、赠送5 |
| principal_first | 本金55、赠送0 | 本金45、赠送10 |

分摊按整数分计算，用累计目标与尾差控制；多次小额消费不累计丢失赠送金。每笔账单持久化实际用到的每个批次、本金、赠送和策略版本，详情不能临时从当前活动推算。算法及退款边界见数据方案。

现有 WC 员工确认扣款、WB 顾客报价确认、WP 充值识别继续复用；三条实际资金路径统一进入 funding 分摊应用接口，不能只改员工扫码路径。WP 仍不授权直接扣款。

顾客账单报价与员工预览显示本次扣本金、赠送和不足补付；确认后明细固定。账户/批次/策略变化时旧报价返回 stale，重新核对；同一成功幂等请求始终恢复原分摊。

余额不足继续只扣可用部分，保留未付差额，由原线下补付流程核实；赠送视作钱包支付权益，不当作商户外部实收。保留零余额授权无零金额流水的规则。

## 8. 退款与纠错

1. **消费退款**：按原账单已持久化分摊返还本金/赠送，部分退款按原扣款组成累计分配，不能按当前规则换成全部本金；外部补付按原凭证退款，不把外部现金变成赠送。
2. **普通无赠送充值退款**：保留原单、部分退款及线下确认流程；额度为原实收未退限额与对应批次/历史本金池可用本金的较小值，不能借赠送金退现金。历史原单也不能借新赠送批次套现，该额度边界变化必须列入迁移验收和发布说明。
3. **赠送批次退出**：首版退款预览列明可退剩余本金和撤销剩余赠送，整批当前未冻结权益退出；占用中的退款/冻结须先处理。先冻结两部分，实际原渠道退本金成功后同时扣除本金及撤赠；取消未执行退款释放两部分，不提前撤赠。
4. 示例：100+10按比例消费55后，退出退本金50、撤赠5，不把55全部当现金退；本金优先消费55后，退45、撤赠10。
5. 充值批次退出后又发生原消费退款，只恢复该消费原实际扣掉的本金/赠送，并保留原批次关系；批次可恢复这些权益，不恢复已撤销的未消费赠送。恢复的本金仍受原实收累计退款上限约束，可以再办理剩余权益退出。
6. 并发消费、退款申请、确认、取消和积分操作均不得产生负数或重复账。资金只追加冲正/退款流水，不编辑旧余额历史或原收款凭据。

原单到期善后规则保持；新营销关闭不阻断已有活动批次的查询、消费退款或实际退款处理。

## 9. 手动积分与兑换

### 9.1 首版功能

- 每个积分计划/顾客一个积分账户，与该顾客是否已有资金钱包余额无关；授权员工可为已建档、手机号完整的有效共享顾客幂等开通零积分账户，无需顾客事先登录。历史无手机号档案先补全再新开户，不复制新顾客来绕过资料维护。
- 增加：填写正整数、原因、备注，确认后产生加分流水。
- 扣减：填写正整数，原因选择“兑换”或“其他调整”。兑换必须填写兑换内容，可加外部参考号；不强制已有商品目录或消费单。
- 顾客只读积分余额、加扣分和兑换明细，没有自助加分/兑换提交权。
- 不创建金币金额，不定义积分兑换现金比例，不影响钱包金额、账单 paid 状态、商户实收或收入报表。

### 9.2 记录与纠错

积分为整数，首版账户余额上限2,147,483,647，余额不能为负。每笔保存前后余额、数量、类型、原因、操作员工、发生门店、时间、可选业务参考号、关联原记录。

积分流水类型：`manual_grant / manual_deduct / redemption / reversal`。操作数均输入正整数，由命令类型决定方向；兑换记录和对应扣积分流水在同一事务生成。

错误通过**原记录全额冲正**处理，不提供编辑/删除流水。原加分已被消费导致余额不足时，禁止冲正为负数，提示先核实；原扣减/兑换冲正则退回原数量。每条原记录最多冲正一次，冲正必须写原因；错误冲正的后续调整另建新有审计命令。

未来商城可在独立兑换订单中调用同一积分扣减/返还端口；商品、核销和库存不塞进本次积分账户服务，也不新增配送模型。

| 活动管理 | 草稿/定时/生效/结束/停用、版本、档位、金额、优先级和影响计划门店 |
| 基础设置 | 基础单档列表、默认分摊方式；修改仅影响新单提示 |
| 顾客充值 | 当前活动、单选档位、应付本金/赠送/合计、渠道、下一步；无自由金额和数量输入 |
| 顾客申请详情 | 待核实/已入账/已取消、原金额快照、付款声明、取消与返回原单 |
| 商户确认 | 实收本金突出显示，赠送/到账合计分开，实收勾选与凭据要求 |
| 钱包首页/流水/账单 | 本金、赠送、可用总计；交易组件明细；历史流水保持原展示并标记为本金 |
| 退款预览 | 现金退本金、钱包本金返还、赠送返还/撤销、冻结与原渠道分项 |
| 积分管理/明细 | 当前积分、加/扣/兑换/冲正、原因、兑换内容、员工、门店和时间 |

所有新页面覆盖空、加载、失败、过期、权限不足、重复提交和网络结果未知状态。支持中英文、手机屏幕、SGD金额格式，业务名称和商户输入内容不自动翻译。手机号、个人资料和 QR 继续使用原安全边界，不把码放 URL 或持久化浏览器存储。

## 11. 报表口径

- 充值实收：仅本金，按现金/PayNow/信用卡分别统计。
- 权益入账：本金入账、赠送入账及合计分列，不把赠送计为现金实收。
- 消费：本金消耗、赠送消耗、钱包合计、外部补付分列，禁止重复累加成实收。
- 余额：本金、赠送及各自冻结；同计划跨店总余额只计一次。
- 退款：原渠道退本金、钱包本金返还、赠送返还和撤销分别列示。
- 积分报表只显示加分、扣分、兑换、冲正和余额，不能与SGD相加。
- 增加总余额/组件/批次/流水一致性指标，发现不一致阻止新资金交易，保留读和受控异常善后。

## 12. 分阶段实施与退出条件

| 阶段 | 交付 | 必须满足后才能继续 |

| 1 资金组件底座 | 历史本金池、批次、冻结、统一分摊、三种扣款及退款 | 默认无活动时旧业务完整通过，账务恒等，无法用赠送退现金 |
| 2 充值营销 | 基础档位、草稿模板、活动发布/优先级/报价/快照、商户单档充值 | 单档校验、并发发布、活动修改及重复确认测试通过 |

## 14. 发布与运行保护

迁移与发布风险的完整设计见配套数据文档。关键约束：默认活动未发布；新顾客申请/积分写入有独立功能开关；先验证资金组件兼容再开放营销。已经出现赠送或积分数据后，不能直接回退到只认识总余额的旧 jar。关闭活动入口不等于删除权益，不阻断已有权益的安全读取和原单善后。

发布前保存数据库、jar、前端及版本文件备份，核对目标 RPB 服务、稳定就绪、PID/InvocationID、日志、业务指纹和其他服务边界；生产资金验收须使用明确的专用测试顾客和范围，不能将普通顾客当测试账户。

## 15. 评审结论与开发准备

- 架构：复用钱包产品、共享顾客、登录、门店主体及 App Gate；活动、资金组件、积分独立职责，积分不依赖钱包资金仓储。
- API：新增路径/DTO/权限/错误/幂等在配套文档定义；旧客户端无法表达活动权益时必须明确拒绝，不静默吞掉赠送。
- 数据：历史视为本金，不重写历史流水、不虚构历史批次归属；新资金必须分组件和批次，冻结、退款及报表同步改造。
- TDD：先资金不变量和迁移，再活动/申请与积分；并发、隔离、退款和真实浏览器作为完成前提。
- 交付：本方案及两份配套设计即本轮成果；实施阶段按0–5顺序推进，具体迁移号按开始实施时最新Flyway版本分配。
