## 已核实的现有控制及其边界

- 顾客电话查找要求角色、`customer.lookup`、门店范围及 App Gate；查询以认证员工的租户为范围，不接受客户端任意租户覆盖。授权人员可见完整联系资料属于业务用途，不能一概视为泄漏。
- 叫号屏要求 `queue.display.view` 和门店访问范围，并非匿名公共 API。此次修复针对多人屏幕输出，与匿名访问控制分别验证。
- 预约分享服务核对 token 的存在、撤销与过期，并使用电话脱敏规则。持有分享链接者仍能查看允许公开的预约内容；链接本身属于访问凭据，应保护日志、转发及引用来源。
- `WalletAccess` 检查租户、员工权限和门店；顾客账户访问检查所属 customer。顾客凭证图片服务额外检查上传者及来源交易归属，按租户/门店读取；接口含 `private, no-store` 和 `nosniff`。本次 API 测试使用 mock，不构成生产数据库隔离证明。
- 顾客登记记录保留实际操作者、自助登记来源、时间及告知正文快照；商户代录确认沿用现有规则。它不证明电话所有权，也不能自动证明所有后续用途合规。
- 顾客会话以随机 token 及服务端哈希存储；当前支付 OCR 实现使用本地 Tesseract。未发现该实现主动调用境外 OCR 服务，但未核实生产部署、服务器位置或第三方供应链。
- 总安全链的 `permitAll` 不单独等于个人资料公开：本项目有控制器、App Gate 和应用服务授权。此次未逐一证明所有 API 的拒绝行为，不能据此作全系统安全通过结论。

## 本次输出规则

1. 正常称呼：首个 Unicode 码点加 `***`，例如虚构姓名 `张小明` → `张***`、`Alice Example` → `A***`。
2. 单字符称呼、带数字或 `@` 的称呼：`***`；空值：`顾客`。同时覆盖当前叫号与候位。
3. 规则在后端 DTO 映射执行，响应中不附原始姓名，避免只在浏览器遮挡。
4. 排队读取日志不输出异常 message、toString 或携带数据的堆栈。减少了故障细节，排障需用稳定事件名、异常类型和受控环境复现。
5. 这是最小化输出，不是不可重识别的匿名化：票号、时间、现场情况仍可能与个体关联。
