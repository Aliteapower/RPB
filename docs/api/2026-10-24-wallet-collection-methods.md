# Wallet collection methods

Scope: tenant + wallet issuer/program, shared by its enabled stores. Existing cash, paynow and credit_card become initial editable subjects. Administrator config is presentation and offline settlement classification, never a new online payment integration.

GET `/api/v1/stores/{storeId}/wallet/collection-methods`: wallet.settings.manage; returns `{version,methods:[{code,name,type}],affectedStoreIds}`. PUT same endpoint `{version,methods:[{code?,name,type}],idempotencyKey}` atomically replaces the active list. New items omit code; server generates immutable `type:UUID`. Types cash/paynow/credit_card/other; changing an existing code's type is forbidden. Names trimmed 1–60 characters, unique ignoring case, maximum 30 active items, minimum one. Array order is display order. Same program settings version uses optimistic concurrency; tenant_admin and current authorized store/AppGate checks are required. Duplicate idempotency keys replay original result; changed payload conflicts. Removed items leave historical identifiers and labels intact, no hard deletion of history.

Both endpoints require an existing wallet program attached to the current store. An unconfigured store first calls the existing PUT `/program` attach/activation operation; it inherits an existing issuer's channels and labels without replacing them. Only then does the editor submit a versioned method update. This prevents initialization from overwriting sibling stores' shared settings. Local security allowlist adds exactly GET and PUT for this resource; other methods remain denied. The existing identity, role, permission and AppGate checks still execute in the controller/application flow.

Program context and topup offers add `channelLabels` map. Existing `channels` array carries active immutable identifiers, no frontend hard-coded choices. Existing request `channel` accepts the selected code. Backend checks active program membership for new operations, while existing pending recharge recovery retains its original subject and settlement requirements. New cash-class methods retain optional cash-topup receipt; PayNow-class methods retain configured account/QR checks. Other offline methods require receipt, account and terminal; no automatic online collection.

Quote captures label and program version in offer snapshot; configuration changes invalidate unconsumed quotes. Topup and collection creation capture subject name; edits/removal never rewrite historical snapshots. Original transactions without custom labels retain original translated category display. Refunds continue to reference actual original collections.

V068 extends allowed channel identifiers (controlled type + optional UUID), adds program label metadata and collection name snapshot. Original balances/ledger unchanged. Old page/API channel values remain valid only while that subject stays active; stale pages receive normal invalid/changed response and must refresh. Full rollback of custom-channel support requires draining pending custom transactions; preserve new data, do not force channel codes back to legacy values.

Rollback qualification: before any custom-code transactions exist, application rollback may retain the additive V068 schema. Once custom-code transactions exist, retaining backend support for those identifiers is necessary for later recovery/refunds and history; use a compatible corrective version rather than reverting directly to the original three-value implementation. Do not delete columns, labels or transactions, and do not restore a dump over newer business activity. Reconciliation groups by immutable underlying type, adds `topupOtherCents`, and collection/refund rows retain the actual subject-name snapshot.

Validation: tenant/admin/AppGate denial, wrong issuer, version conflict, duplicate names/codes, invalid/mutated types, min/max, add/edit/reorder/delete, historical label immutability, disabled quote rejection, pending recovery, cash/no receipt, PayNow configured checks, other receipts, customer and merchant pickers, stable idempotent settlement, original reports/refunds. Runtime uses target/local-postgres-current.txt only; isolate test schemas. This round no commit/push/deploy.
